# الفاتورة الإلكترونية — تكامل مصلحة الضرائب المصرية (ETA)

> ## تنبيه صريح: غير مُجرَّب على ETA الفعلية
>
> هذا التكامل **لم يُجرَّب مطلقًا على بيئة مصلحة الضرائب (لا التجريبية ولا الإنتاج)**.
> كل الاختبارات تعمل ضد محاكاة HTTP (`httpx.MockTransport`) تثبت سلوك النظام نفسه فقط.
> أسماء الحقول وأكواد الضريبة الفرعية (`V009`/`V003`) والتسلسل القانوني للتوقيع ومسارات الاستعلام
> والإلغاء وكود "المستند المكرر" مكتوبة من وصف الـ SDK العام وقد تحتاج تعديلًا.
>
> **قبل أي استخدام فعلي يلزم:** (1) شهادة توقيع رقمي (USB token / HSM) وخدمة توقيع،
> (2) `client_id` / `client_secret` من بوابة ETA، (3) تجربة كاملة على **البيئة التجريبية (preprod)** ومراجعة
> المحاسب لكل نوع مستند. لا تفعّل الإنتاج قبل اجتياز البيئة التجريبية.

## ما الذي يفعله

1. يحوّل `Invoice` / `CreditNote` إلى مستند ETA JSON إصدار 1.0 (`documentType` = `I` للفاتورة و`C` للإشعار الدائن).
2. يوقّع المستند عبر **Signer قابل للتوصيل** (لا يوجد تشفير فعلي داخل النظام).
3. يرسله (OAuth `client_credentials` ثم `POST /api/v1/documentsubmissions`) ويتابع الحالة، مع طابور وإعادة محاولة.
4. يحفظ الحالة على الفاتورة: `eta_status`, `eta_uuid`, `eta_submission_id`, `eta_long_id`, `eta_internal_id`, `eta_submitted_at`, `eta_errors`.

الإرسال **لا يُنتج أي قيد محاسبي ولا حركة مخزون** (الإيراد/الضريبة/الذمم سُجّلت وقت إصدار المستند أصلًا).

## الإعداد (أدمن)

من `PUT /api/v1/einvoice/settings` (أو شاشة الإعدادات): `enabled`, `environment` (`preprod`|`prod`|`custom`),
`tax_registration_number` (9 أرقام), `activity_code` (4-6 أرقام), بيانات عنوان المُصدِر
(`governate`, `region_city`, `street`, `building_number`, `branch_id`), `client_id`, `client_secret`,
`signer_mode` (`none`|`mock`|`external`) و`signer_url` / `signer_token`، وافتراضيات الأصناف
(`default_item_type` = `EGS`|`GS1`, `default_item_code`, `default_unit_type`, `vat_subtype`, `zero_vat_subtype`).

* `client_id` / `client_secret` / `signer_token` **write-only**: تُحفظ مشفّرة (Fernet، بادئة `v1:`) ولا تُعاد في أي استجابة؛
  الإرسال بدونها = إبقاء القيمة، و`clear_client_secret` / `clear_signer_token` للمسح.
* مفتاح التشفير: متغير البيئة **`ERP_EINVOICE_KEY`** (مفتاح Fernet — موصى به). وإلا يُشتق من مفتاح JWT الخاص بالتثبيت
  (`jwt_secret.key`). **تغيير المفتاح يجعل الأسرار المخزنة غير قابلة للفك**: يظهر خطأ عربي واضح ويُعاد إدخالها.
  النسخ الاحتياطي الكامل (dump) يحتوي النص المشفّر؛ حمايته من حماية المفتاح. أسماء الأعمدة تحتوي `secret`/`token`/`credential`
  فيستثنيها سجل التدقيق وتصدير الورشة تلقائيًا.
* رقم التسجيل الضريبي للـ ETA يُخزَّن هنا (وليس في `WorkshopProfile.tax_id` الذي يبقى قيمة العرض/الطباعة).

## التوقيع الرقمي (Signer)

النظام **لا ينفّذ تشفيرًا**. أوضاع `signer_mode`:

* `none`: غير مضبوط — الإرسال مرفوض.
* `mock`: توقيع وهمي (`base64("MOCK:" + sha256)`) للاختبار والبيئة التجريبية فقط. **محظور على `prod`** في ثلاث طبقات:
  عند حفظ الإعدادات، وعند الإرسال، وفي معالج الطابور (يرفض حمولة موقّعة وهميًا لو البيئة صارت إنتاج).
* `external`: خدمة توقيع خارجية تملك الشهادة (USB token/HSM). البروتوكول:

```
POST {signer_url}                (https فقط)
Authorization: Bearer {signer_token}      (إن وُجد)
Content-Type: application/json

{ "canonical": "<النص القانوني المُسلسل>", "document_hash": "<sha256 hex للنص القانوني>" }

200 OK
{ "signature": "<base64 CMS/CAdES-BES>" }
```

النظام يضع القيمة في `signatures: [{ "signatureType": "I", "value": <signature> }]`. مهلة الاتصال 20 ثانية،
أي رد غير 200 أو توقيع غير base64 أو يبدأ بـ `MOCK:` يُعتبر فشل توقيع (رسالة عربية، لا إرسال).

النص القانوني (`serialize_for_signing`): أسماء الخصائص بحروف كبيرة، كل قيمة بين علامتي اقتباس، والمصفوفات تكرّر اسم الخاصية قبل
كل عنصر، وخاصية `signatures` مستبعدة. **غير مُتحقَّق منه ضد مدقّق ETA الفعلي.**

## دورة الحالة

`NULL` (لم يُرسل) → `queued` → `submitting` → `submitted` → `valid` | `invalid`
`submitting` → `failed` (مؤقت، يعيده العامل) أو `rejected` (رفض دائم: صحّح البيانات ثم أعد الإرسال)
`valid` → `cancelled` (أدمن، سبب 3-200 حرفًا).

* **المقفول** في الـ ERP: `queued`, `submitting`, `submitted`, `valid` — لا تعديل ولا حذف ولا إلغاء (فاتورة أو إشعار دائن)،
  حتى لا يختلف الـ ERP عن ETA. الحراس تُنفَّذ قبل الموافقات وقبل أي عكس (لا آثار جانبية). للتصحيح: إشعار دائن، أو إلغاء لدى المصلحة (أدمن).
* `cancelled`: لا تعديل ولا إعادة إرسال (الرقم الداخلي `internalID` محروق)؛ الحذف مسموح.
* `rejected` / `invalid` / `failed`: قابلة للتعديل ثم `resubmit` (يعيد بناء المستند من البيانات الحالية).
* الإشعار الدائن يتطلب فاتورة أصلية `valid` (يحمل `references: [uuid الأصلية]`).

## الطابور وإعادة المحاولة

* الحمولة الموقّعة تُحفظ وتُعتمد (commit) **قبل** أي اتصال، والإعادة ترسل **نفس الحمولة ونفس `internalID`** (يمنع تكرار المستند).
* claim ذرّي (`UPDATE ... WHERE status IN ('queued','failed')` وفحص `rowcount`) + صف تسليم واحد لكل مستند (UNIQUE) → ضغطتان/طلبان متزامنان = اتصال واحد.
* العميل: أخطاء الاتصال و5xx و429 تُعاد بـ backoff 2s/4s/8s + jitter (يحترم `Retry-After` بحد 60s)؛ 401 = إعادة مصادقة مرة واحدة؛ بقية 4xx لا تُعاد.
  طلب الإرسال من الواجهة يحاول **مرة واحدة** (بلا نوم داخل الطلب) ويعيد `202` عند عطل مؤقت؛ العامل يعيد المحاولة بتأخير `min(2^n × 60s, 6h)`، وبعد 8 محاولات تتوقف التلقائية (`next_attempt_at = NULL`) ويلزم إعادة إرسال يدوية.
* رفض "مستند مكرر" يُسوّى بالاستعلام (`documentsubmissions/{id}` أو `documents/search?InternalID=`) بدل إنشاء مستند ثانٍ؛ المطابقة بالنص لأن كود الخطأ الفعلي غير مُتحقَّق منه، وعند الفشل يبقى `failed` للتحديث اليدوي (`refresh-status`).
* صفوف `submitting` العالقة أكثر من 10 دقائق تُعاد لـ `failed`.

## نقاط النهاية (`/api/v1/einvoice`)

`GET /status` (الكل) · `GET|PUT /settings` و`POST /settings/test-connection` و`POST /queue/run` و`POST …/cancel` (أدمن) ·
`GET …/preview` و`POST …/submit` و`…/resubmit` و`…/refresh-status` و`GET /submissions` (أدمن/محاسب) · `GET /documents/{invoice|credit-note}/{id}` (الكل).
المشاهد (viewer) قراءة فقط. الورشة تؤخذ دائمًا من الـ JWT. خطأ التحقق من المستند = `422 {detail, errors[]}`.

## قيود معروفة

* **غير مُجرَّب على ETA** (انظر أعلى الصفحة). الاختبارات على SQLite ومحاكاة فقط؛ لم يُجرَّب Postgres.
* الـ ERP يخزن ضريبة وخصمًا واحدًا على مستوى المستند بينما تتحقق ETA لكل بند: يُوزَّع الخصم بالتناسب والبند الأخير يمتص الباقي،
  و**حارس مطابقة** يمنع الإرسال لو اختلف إجمالي ETA المحسوب عن إجمالي المستند بأكثر من 0.01.
  معادلة الإشعار الدائن تحسب الضريبة قبل الخصم (على عكس ETA)، فالإشعار الذي يجمع خصمًا وضريبة يُمنع إرساله بالحارس.
* الضريبة الصفرية: النوع الفرعي `zero_vat_subtype` (افتراضي `V003`) غير مُتحقَّق منه — يراجعه المحاسب (ويظهر تحذير).
* عنوان العميل نص حر فلا تتوفر المحافظة/المدينة/رقم المبنى المفصّلة للمستلم من نوع منشأة (يظهر تحذير).
* ETA تقبل التواريخ الرجعية بحدود (~7 أيام): الفواتير الأقدم تظهر بتحذير وقد تُرفض.
* رمز QR: يوفّر الخادم `qr_text` / `share_url` للمستند `valid` فقط، والرسم يتم في الواجهة.
